1 · The hourly run

Everything in production starts from one systemd timer at five past each hour. hourly_job._run() runs four phases in order, and a failure in one phase is recorded in the status, not raised to the timer.

1 · Ingest live

live_bridger.run_bridger() loads symbols, funding schedules and intervals once (get_symbols, prefetch_global_funding), then runs process_symbol in threads for every symbol:

  • _update_klines: new closed 1h candles, paginated, with the cheapest weight bucket (_kline_limit)
  • _update_funding: only when funding_call_needed says a settlement has closed
  • _update_metrics via _fetch_metrics_pages: open interest and top-trader long/short (Binance keeps 30 days)
  • Every write goes through _append_shard (atomic); watermarks live in SyncStateManager

2 · Compute live

live_runner.run() finds assets (discover_assets), loads engine_state.json, and runs process_live_asset in a process pool:

  • load_with_oi joins the price shard with OI, long/short and funding
  • validate_asset_data is the circuit breaker: 720+ bars, current, no bad prices
  • compute_features over full history, then step_cta for each new, closed bar only (bar_is_closed)
  • Closed trades are de-duplicated (dedupe_new_trades) and appended; open trades are rebuilt with active_trade_record

3 · Gate + status live

  • Fails closed if the data root has under V10_MIN_SHARDS shards
  • write_all_trades_view rebuilds all_trades.csv
  • new_signals lists positions entered in the last 24h
  • raw_fresh_pct and failure ratios decide ok (80% fresh, ≤20% failures)
  • Status goes to hourly_status.json, and append_status_history adds it to the history

4 · Publish live

  • ops.backup: ledgers and state to latest/ every hour, daily/ at 00 UTC, and the shard mirror once a day
  • ops.publish_site calls site_export.export_site, then uploads with cache headers
  • send_report builds the email with render_report and sends it with send_report_sns, or SES as a fallback
  • ops.heartbeat puts the V10/HourlyOK metric; the alarm fires on missing data

2 · One hourly bar through the engine

cta_dual.step_cta(ts, row, state, cfg, asset) is the whole trading logic. It runs once per closed bar per asset, with that asset's saved state: open trades, the ignition "armed" countdown and the PHOENIX watch list.

8 · Deployment and infrastructure

deploy/aws/deploy.sh (run on your Mac)

  • deploy: S3 bucket and lifecycle, SNS, IAM role, own VPC if needed, EC2 t4g.small, alarm
  • update: packages the code (build_release) and runs refresh.sh on the server over SSM
  • dashboard: publishes the site and sets up CloudFront with origin access control
  • run-now, status, logs, verify, diag, resubscribe, destroy (keeps the bucket)

On the server

  • bootstrap.sh (first boot): Python venv at /opt/v10_venv, user v10, ops restore, timer on
  • refresh.sh: unpacks a release into the read-only /opt/v10_standalone
  • Settings in /etc/v10/v10.env (template: deploy/v10.env.example)
  • Writable paths are only /var/lib/v10 and /var/log/v10

Access and alternatives

  • create-deployer-user.sh + deployer-policy-*.json: scoped IAM for the person deploying
  • Dockerfile: the same hourly job in a container, with data mounted at /app/data
  • requirements*.txt: pinned runtime, dashboard extras, and test tools

9 · Code that exists but never fires

Found while mapping. None of these change what runs today; they explain gaps between the documented design and the live behaviour.

The upper-wick filter and the exhaustion exit are inactive. step_cta reads upper_wick_ratio, but nothing computes it, so it is always 0. The "wick ≤ 0.65" entry veto always passes, and the exhaustion exit (which needs a wick above 0.40) can never trigger. There are no exhaustion exits among the 4,009 closed trades.
Two trap regimes are never set. regime_euphoria and regime_dead_cat are read by the entry gate and the squeeze exits but never computed. Only is_toxic_distribution actually blocks entries or triggers regime_bailout.
Most CtaConfig knobs are not wired in. step_cta reads only the Donchian fields (and a slippage attribute CtaConfig doesn't define, so the 0.2% default applies). The −20%, +5%, 25% trail, 12-bar arming, 14-day PHOENIX window, 0.65 wick and 0.8 OI ratio are literals in the code. Changing hard_stop_pct, volume_shock_mult or max_ignition_wick_ratio in config.py does nothing.
Computed and unused: l5_rank_pctile (the whole L5 ranking pipeline), oversold_squeeze_long, is_overheated in exits, and strict_ignition/ignition_signal from features.enrich. The engines use hyper_ignition.
The toxic-trail exit books the trail level, not the price. exit_price = trade_max_high × 0.75 even when the hourly close is lower. The costed backtest measured it: +59.6% booked against +32.4% when filled at the next open.
